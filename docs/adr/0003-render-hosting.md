# ADR 0003: Render for the API, and the cold start that comes with it

- Status: Accepted
- Recorded: 2026-10-07 (the service already runs this way)

## Context

The API is a long-lived ASGI process. A Gemini call uses a 30 second client timeout, which is longer than a short serverless limit. `docs/deployment.md` records that Vercel Hobby functions time out at 10 seconds, so the API does not run there.

## Decision

`render.yaml` defines a Python web service named `gold-queen-api` in Oregon on the free plan. The build installs `requirements.txt`. The start command is `uvicorn app.main:app --host 0.0.0.0 --port $PORT`. The health check path is `/health`, which does not touch Postgres or Gemini. `ENVIRONMENT` is `production`. `ALLOW_REGISTRATION` is `false`. `JWT_SECRET` is generated by Render. `DATABASE_URL`, the Pluggy credentials, `GEMINI_API_KEY`, and `CORS_ORIGINS` are `sync: false`, so they are not committed.

## Consequences

The free service sleeps after 15 minutes without traffic and takes about 50 seconds to wake. The first request after that pause waits for the process. The in-process login throttle resets on that start and is not shared with any other instance. The keep-alive workflow retries `GET /health?db=1` for up to two minutes so a cold start can still reach Supabase. Pointing the Render health check at `?db=1` or `?deep=1` would make every probe hit the database or Gemini; the blueprint leaves it on `/health`.

## Alternatives

Hosting the API as Vercel functions was rejected because of the 10 second timeout against Gemini. An always-on paid instance would remove the sleep; the blueprint pins `plan: free`. A second worker would not see the login counters, which is why that limiter stays documented as per-process.
